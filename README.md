# Hologram Model Hub

The goal: a decentralized, drop-in replacement for the Hugging Face Hub. Every
tensor named by its content address, every release a signed manifest, bytes
from any source, and every decision the hub makes about a request taken by a
Prism application whose rules Lean proves. A user sets `HF_ENDPOINT` and
`huggingface_hub`, transformers, vLLM and llama.cpp keep working unchanged.

What exists today: the hub kernel and the hub's interface, below. No runner in
this repository serves Hugging Face requests yet; the catalog the interface
shows is read from the live hub at gethologram.ai, which is still the one in
`hologram-live`. The plan is in [docs/brief.md](docs/brief.md); what was
measured before building is in [docs/phase1-study.md](docs/phase1-study.md).

This repository was created from the
[UOR Prism template](https://github.com/UOR-Foundation/template), so its gate,
SDK pin and claim discipline are the template's. The sections below the hub
kernel describe that template.

## The hub kernel

`app/` is the hub kernel: the pure decision core every runner calls. It decides
nothing that needs a network, a clock or a disk; runners gather facts, ask the
kernel, and carry out its plan.

| Request | Bytes | What it holds |
| --- | --- | --- |
| resolve | 104 | runner (edge or local), repository state, revision, entry kind, source pin, four candidate sources (holds, healthy, vetted, failed), the requested revision and the release's commit |
| accept | 81 | expected and observed SHA-256, expected and observed size |

The answer is always three bytes: an answer code, the chosen source slot (4 for
none) and the ETag kind (1 git blob SHA-1, 2 SHA-256, 0 none). Codes: 1
redirect, 2 serve, 10 repository not found, 11 revision not found, 12 entry not
found, 13 gated, 14 disabled, 15 unknown source, 16 source lacks the file, 17
no source, 20 deliver, 21 quarantine, 0 invalid request.

Lean proves ten claims for every possible request, registered as `HK-01` to
`HK-10` in `model/ids.toml`, specified in `features/suites/kernel.feature` and
pinned by `crates/conformance/tests/kernel.rs`. Each theorem has its own module
in `app/src/Proofs/`.

| ID | Claim |
| --- | --- |
| HK-01 | A missing and a private repository get the same answer, and nothing is delivered |
| HK-02 | A file is delivered only for a public repository at a resolved revision whose entry exists |
| HK-03 | The edge runner only redirects; the local runner only serves |
| HK-04 | The edge runner never redirects to a source that is not vetted |
| HK-05 | A delivered file has a source, and that source holds it and has not failed verification for it |
| HK-06 | A pinned source is the only source the kernel may choose |
| HK-07 | Without a pin, a healthy source is chosen whenever a usable one exists |
| HK-08 | Small files carry the git blob ETag, large files the SHA-256 ETag |
| HK-09 | A commit prefix resolves only at 7 to 40 characters, and only if it matches |
| HK-10 | Received bytes are delivered exactly when their digest and size are the expected ones |
| HK-11 | Every header item and every link that stays in the hub opens a screen the kernel renders |
| HK-12 | A tool sees a status below 400 exactly when the kernel delivers; every refusal is a 4xx or 5xx with a named error code |
| HK-13 | The page says Verified only when at least one source delivered and none sent other bytes; any mismatch is reported as one |
| HK-14 | A model page says Witnessed or Published only when every signature check passed, Published only for the namespace owner's publisher signature, and never shows a witness as a publisher |
| HK-19 | A source that is not vetted is chosen only for a file whose address the record names |

`app/src/Kernel.lex.tex` and `app/src/Proofs/` are generated by
`python app/tools/gen_kernel.py`, which also computes the 33 acceptance vectors
from an independent reference implementation of the same rules. The pinned
tests are written once by `python app/tools/write_tests.py .` and then owned by
hand: a changed claim fails them until a person agrees to it.

## The hub interface

`web/` is the hub's site, published at the root of this repository's Pages
site, with the proof page under `app/`. Its look is gethologram.ai's own: the
shell, header, controls, landing, catalogue and model page in `web/hub.css` are
that site's `chrome.css` and `styles.css`, trimmed to what this hub draws, and
`web/icons.mjs` carries its icon set and the mesh behind every card. Every
value still resolves to the brand kit (`app/brand/hologram-warm.css` for the
colours and families, `web/tokens.css` for the scales).

The site decides nothing: every label, route, header item, link, facet, tab,
sort, parameter stop, command and the whole Hugging Face dialect table come
from `app/src/Site.lex.tex`, and the browser gets them by asking the verified
holo.

1. The page loads `app/app.holo` with `prism-code`'s browser runtime, which
   checks its identities.
2. For each screen it sends the guest `03 nn` and draws the JSON it returns.
3. It reads the catalogue from `data/models.json`, the copy `tools/web-data.mjs`
   takes at each deploy, and a model's files from the hub's own Hugging Face
   API (`/api/models/{repo}/tree/{revision}`).
4. After first paint it replays every acceptance vector the holo carries and
   says so in the footer.
5. Verify on a model page fetches the smallest addressed file from each source
   through the hub's `/via/<source>` route and hashes it in the browser; the
   kernel's accept rule (`HK-10`) judges each copy and its verdict rule
   (`HK-13`, request `04 r0 r1 r2 r3`) decides what the page says.

The page and the wire read one index. `tools/index.mjs` writes browse shards
beside the release records, one row per release, carrying the facets the page
filters on — task, parameter count, family, architecture, languages, format,
library, licence, source and status — derived by `tools/facets.mjs`, the one
place the hub decides what those are. The root names each shard by the hash of
its bytes and names the rule that derived the rows, so the page checks a shard
before drawing it, with the kernel's accept rule, and says whether the listing
it is holding is signed. `tools/web-data.mjs` now copies only what the index
does not carry: the registry, the apps list, and one avatar per owner, fetched
from Hugging Face's avatar CDN at the size that CDN stores and copied whole.
The filters are
grouped as Hugging Face groups them (Main, Libraries, Languages, Licenses,
Other), and Parameters is one bar with two handles over the stops the screen
names, rather than a row of buckets.

The theme switch is the Prism frame's panel: the three looks as one segmented
control, a search of Unsplash, nine pictures and the photographer's line. The
three wallpapers this site ships come first; everything else is fetched through
the frame's Unsplash worker, which holds the one key every Prism app shares, so
no page here carries a key. Choosing a photo reports the use to Unsplash, as
its licence asks, and credits the photographer with a link.

The browse page speaks Hugging Face's query language. The filters write
`pipeline_tag`, `num_parameters`, `library`, `language`, `license` and
`author`, the search box writes `search`, the pager writes `p`, and the
slider writes a pair of the stops' own labels (`num_parameters=6B,32B`), so a
link copied from huggingface.co with the host changed opens the same view
here. The hub's own facets carry a `hub_` prefix and cannot collide with one.
`HK-16` proves every facet maps to one parameter and back.

A program that reads this index may depend on part of a record. `HK-18` holds
that part fixed: the repository, the revision, every file's `path`, `size` and
`gitSha1`, `sha256` where the source publishes one, and the sources that hold
it. The rest of a record is still moving. The claim is a test rather than a
proof, because a proof cannot catch a field being renamed in JavaScript, and
the test reads the builder itself.

A file may have more than one witness. Hugging Face publishes a SHA-256 only
for LFS files, so `tools/index.mjs` also reads Pirate Face's per-file hashes
for the same revision and keeps them in a `witnesses` block, with the party
that gave each and the day it was read, never in `files[].sha256`, which the
edge reads to decide a client's ETag. The kernel decides what two witnesses
add up to (`HK-17`): an address is used when both name it and agree, the page
says so when one names it alone, and a file whose witnesses disagree has no
address at all. On `openai-community/gpt2` that takes the files a reader can
check from eleven of twenty-six to twenty-five, so Verify picks a file of a
few hundred bytes rather than a few hundred megabytes.

A release record carries ten fields, and the kernel decides whether they are
enough. `tools/index.mjs` writes the revision, every file, the tags as
published, the task, the library, the config, the card's front matter and the
address of its bytes, the parameter counts, the last change and whether the
publisher gates access. Operation 6 answers from those facts: answer from the
index, ask the source dialect, or answer and say the answer is partial
(`X-Hub-Partial` names the absent fields). An incomplete record is never
served as though it were whole, and `HK-15` proves there is no input for which
it could be. Counts of another host's traffic - downloads and likes - sit
under `observed`, which names the host and the day they were read, because
nobody holding a copy of the index can re-derive them.

Registry, Apps and Buckets are screens of the kernel too. The registry and apps
lists are copies of the live hub's, taken at each deploy by `tools/web-data.mjs`
because the live hub does not let another origin read them; each page shows
the copy's source, date and SHA-256. Buckets explains account storage, which
stays on gethologram.ai, and checks any object by its address: the page
fetches it from the hub's object store, hashes it with the address's own hash
(BLAKE3 or SHA-256) and asks the kernel's accept rule.

Witnessed models carry a signed manifest. `tools/manifest.mjs` downloads each
model listed in `manifests/models.txt` from Hugging Face, re-hashes every
safetensors file and every file of 10 MB or less, refuses the manifest if any
byte differs from Hugging Face's address for it, and records a BLAKE3 address
for every tensor. `pages.yml` signs the manifests with this repository's
workflow identity through Sigstore (keyless, `actions/attest`), so the
signature lands in the public transparency log. On a model page the browser
checks the bundle against the Fulcio intermediate and Rekor key the model pins
(`web/sigstore.mjs`: certificate chain, validity at signing, the log's signed
entry timestamp, the envelope signature, the workflow identity, the subject
digest and the statement type), and the kernel's trust rule (`HK-14`, request
`05` and ten facts) decides the label. The Tensors tab lists every tensor's
address.

An owner can be indexed whole. `manifests/owners.txt` names owners rather than
repositories, and every public model Hugging Face lists under that name is
indexed, trending or not; `HOLOGRAMTECH`, the Hologram Technologies
organization, is the first. The name is Hugging Face's own spelling, letter
for letter, and an owner that lists nothing fails the build rather than
indexing nothing quietly. A model reaching the index this way is listed,
browsable and downloadable through the hub, but the hub holds no mirror of it:
the live hub has never seen it, so its `sources` are empty and the kernel has
only Hugging Face to send a file request to. The file still arrives, addressed
and with the index's own ETag and size, and a request pinned to another source
is refused `SourceHasNotGotIt` rather than guessed at (`HK-05`, `HK-06`). What
is missing is a second copy, not the file.

With Hugging Face switched off the edge answers the listing from the browse
shards: the same eleven-field row, the accepted sorts, `filter`, `author`,
`full`, `config`, `expand[]` and a cursor in a `Link` header, and the same
refusals - an unknown sort or a direction other than `-1` is a 400, not a
quiet default. `/api/models-tags-by-type` and `/api/quicksearch` answer for
what the index holds, and `/api/models/{repo}/commits/{revision}` returns the
one commit it holds with `X-Hub-Partial: history`.

## The edge runner

`edge/edge.mjs` answers the Hugging Face Hub's read surface, so
`HF_ENDPOINT=<its origin>` works for `huggingface_hub`, `hf`, transformers and
the rest. It is a stateless fetch handler; `node edge/serve.mjs [port]` runs it
on Node 22. At start it loads the kernel holo the Pages site publishes, checks
its identities and replays its examples.

- A file request (`/{repo}/resolve/{revision}/{path}`, optionally
  `/via/<source>/...`) is decided by the kernel: the edge gathers the facts
  (the release and file from Hugging Face's API, which sources hold the file
  from the hub's index, each source's health) and sends the kernel's resolve
  request; the answer becomes HTTP through the kernel's own dialect table. It
  only ever redirects, and only to vetted sources (`HK-03`, `HK-04`).
- Metadata routes (`/api/models...`, tree, paths-info, refs) are Hugging Face's
  own answers, with next-page links pointing at the edge and the Xet fields
  removed from listings, so a client always asks the edge which source to use.
  A Xet read token is passed through: a client asks for one only after its HEAD
  followed the kernel's redirect to Hugging Face, so the bytes still come from
  the source the kernel chose.
- `tests/edge/` runs the Hugging Face client against huggingface.co, against
  the edge, and against the edge with every file pinned to IPFS, and requires
  the same results; `.github/workflows/edge.yml` runs it on every push.

The edge answers first from the hub's signed index (`tools/index.mjs`, built and
signed at each deploy): one record per model in the catalog, every
witnessed model and every model of an indexed owner (its release commit, each
file's size, git and SHA-256 hashes,
and which sources hold it), a catalog, and a root naming every record by
SHA-256. Only the root is signed (Sigstore, keyless, statement type
`https://hologram.foundation/hub/index/v1`, pinned in the model); the edge
checks that signature with `web/sigstore.mjs` and each record against the
root. For an indexed model it answers model info, the file tree, paths-info,
refs and every file request without calling Hugging Face; only a model the
index does not hold is asked of Hugging Face. `HF_API=off` turns that off,
and `DRAIN=huggingface.co` takes Hugging Face out of the sources, so the kernel
sends files to ModelScope or IPFS. The index is a directory of static files any
host or IPFS can serve; `INDEX_URL` points an edge at a mirror.

`edge/Dockerfile` (Node 22, pinned by digest) runs it anywhere containers run.
It is not deployed yet: where it runs is a choice of account. Cloudflare Workers
does not fit, because it does not let a worker compile WebAssembly from bytes at
run time, which loading a holo needs (Cloudflare's documented restriction, not
tested here); any host that runs Node 22 does.

`pages.yml` gives every route its own page (`tools/web-routes.mjs`: catalog,
docs, registry, apps, buckets and each model the catalog lists when the site is
built), so deep links answer 200. After each deploy a `smoke` job opens every screen in Chromium (`tools/smoke.mjs`) and fails unless each draws its screen
and replays every example.

## The local runner

`runner/local.mjs` answers the same Hugging Face read surface, and carries the
bytes instead of redirecting to them. `node runner/serve.mjs [port]` runs it;
`HF_ENDPOINT=http://127.0.0.1:8788` and an unmodified `huggingface_hub`, `hf`,
transformers or llama.cpp downloads through it.

It decides nothing either. It gathers the same facts the edge gathers and asks
the same kernel with `runner` set to 1, which `HK-03` answers `serve` rather
than `redirect` for every input. What it adds is that it checks what arrives
before passing it on, and that it can reach a source no `302` can name.

| | Edge | Local runner |
| --- | --- | --- |
| Carries bytes | never | always |
| Sources | huggingface.co, modelscope.cn, ipfs | those three and `pirateface` |
| Integrity for the client | the client's own check, if it makes one | every byte, before it is served |

The fourth slot is the BitTorrent swarm Pirate Face indexes, and it is never
vetted. That is not a judgement about Pirate Face: a vetted source is one the
edge may redirect a client to, and no client can be redirected to a magnet
link. `HK-04` keeps the swarm off the edge, and `HK-19` keeps it off any file
whose bytes could not be checked afterwards. Both are proved for every input,
so neither is enforced by the runner's own code.

`runner/swarm.mjs` is a leeching BitTorrent client with no dependencies: an
HTTP tracker announce, the peer wire protocol over TCP, and a piece handed on
only when its SHA-1 equals the hash the torrent's infohash committed to.
`runner/torrent.mjs` recomputes that infohash from the metadata's own bytes, so
a `.torrent` fetched from a host nobody trusts is refused unless it hashes to
the infohash the magnet named. It does not seed, speak UDP trackers or the
DHT, or use BEP-19 web seeds. The last is deliberate: measured 2026-11-14, a
Pirate Face web seed answers with a redirect to a volunteer which redirects to
huggingface.co, so using one would build a failover path that ends at the host
it was failing away from (`TEMPLATE-VERIFICATION.md`).

Every response is hashed before it is sent, including one served from the
cache, so nothing reaches a client that the kernel has not just accepted. That
costs a pass over the file per request, which is the price of the guarantee;
a `HEAD` is answered from the record alone and fetches nothing.

Bytes that pass are kept in a cache addressed by their SHA-256, so another
release naming the same file is already holding it. The cache is a shortcut and
never an override: when the kernel answers that no source can serve a file, the
runner does not reach past it, because a delivered file always has a source
(`HK-02`, `HK-05`).

## Pulling from the swarm

A file is served only after every byte of it has been checked, so a cold fetch
from the swarm answers nothing until the whole file has arrived and hashed:
measured at 48 seconds for 125 MB from four seeders. `huggingface_hub` gives up
first. Its read timeout is ten seconds and it sees silence rather than
progress, then retries, and before fetches were coalesced each retry started a
competing download of the same torrent.

Streaming pieces as they arrive is not the answer. BitTorrent checks each piece
against the infohash, so streamed bytes would be intact, but the infohash comes
from the swarm's own index; only the address in this hub's signed record says
the torrent is the file it claims to be. Streaming would send bytes before that
was settled, which is what `HK-19` exists to prevent.

So the wait moves to something that is not a Hugging Face client:

    CACHE_DIR=~/.hologram node runner/pull.mjs openai-community/gpt2 64-8bits.tflite --via pirateface

fetches, verifies and leaves the bytes in the cache under their SHA-256. A
client pointed at the runner with the same `CACHE_DIR` is then answered at
once, from bytes the kernel has already accepted.

## Finding what the swarm has

Pulling is half of it. Pirate Face indexes far more models than this hub does,
so what the swarm holds cannot be answered from this hub's index alone.

    node runner/discover.mjs qwen

searches its catalog and prints the models with a torrent, by seeders. The
runner answers the same question over HTTP for one model, and adds the part
that matters here:

    GET /api/swarm/{repo}

returns the revision, whether it is the revision this hub's record names, the
seeder count, the infohash recomputed from the metadata rather than believed,
the file and piece counts, and `servable`: how many of the release's files this
hub holds an address for. Those last two numbers are deliberately separate.
Peers decide whether bytes can be fetched; addresses decide whether they can be
believed. A model with peers and no address is one you can download and cannot
check, and `HK-19` refuses it rather than serving it.

`tests/runner/` covers it: the torrent, UOR and discovery checks need no network,
`tests/runner/kernel.mjs` pins the kernel answers the runner is built on, and
`tests/runner/serve.mjs` runs the whole path against sources that serve the
right bytes and the wrong ones. `tests/runner/live-pirateface.mjs` is a live
check against the real swarm and is not part of `just vv`.

## Addresses

The hub carries three addresses for the same bytes, because three readers need
three different ones. `sha256` is what a Hugging Face client knows a large file
by and what `HK-10` decides on. The git blob SHA-1 is the identity Hugging Face
gives a small file and the ETag `HK-08` returns for one. `blake3`, taken per
tensor over the tensor's own raw bytes, is the UOR address: a file address says
the file is intact, a tensor address says which tensor is intact and follows
those bytes into any container that holds them.

`tools/manifest.mjs` writes the tensor addresses after downloading and
re-hashing a model itself, and the workflow signs what it writes. The local
runner checks them with `runner/uor.mjs` when a signed manifest names the file,
and reports the count in `X-Hub-Tensors`. A file that passes its SHA-256 but
fails a witnessed tensor means two signed artifacts disagree, and is refused
rather than served.

`app/tools/site_spec.py` is the authoring input for the site; the generator
writes it into `Site.lex.tex`. `web/` holds the renderer (`hub.mjs`), the stylesheet (`hub.css`), a `sw.js` that retires the worker the proof page left at the root, the
full brand fonts (SIL OFL, from hologram-brand-kit at
`caa064a`) and the Alpine wallpaper from gethologram.ai.

## What you get

| Feature | What it means |
| --- | --- |
| **One gate** | `just vv` is the whole acceptance boundary, locally, in the devcontainer and in CI. Each check in it runs once. |
| **One SDK** | `prismpm.lock` pins the SDK image by digest for both `linux/amd64` and `linux/arm64`. Compiler, Lean, Rust, `cargo-deny` and `prismpm` all come from it. |
| **Claims you can audit** | `model/` registers every claim with an honesty level, and `CONFORMANCE.md` is generated from it. A claim without a scenario and a test fails the build. |
| **A scaffold for the discipline** | `just new-capability` writes the register row, the scenario and the failing test in the order the rules require. |
| **A minimal trust root** | `bootstrap.yml` has read-only permissions, no publication credentials, and is byte-bound by `template.lock`. |
| **A release pipeline** | `prismpm.yml` builds once, signs, promotes and deploys the same digest, with every step behind its own protected identity. |

## Get started

You need Git, Docker with Buildx, and a devcontainer client such as VS Code or
the `devcontainer` CLI. Nothing else is installed on the host.

1. **Create your repository.** Choose [Use this template](https://github.com/new?template_owner=UOR-Foundation&template_name=template), then clone it.
2. **Name it.** Set `workspace.package.repository` and `homepage` in `Cargo.toml`, and replace this README with your project's name and purpose.
3. **Open it in the devcontainer.** It runs the exact SDK image `prismpm.lock` selects.
4. **Run the gate.** `just vv` passes as cloned. It builds and verifies the template's own Prism application (below), so you start from a working, proved, shipped example.
5. **Add your first capability.**

   ```sh
   just new-capability CX-01 build parsing "A parsed document round-trips"
   ```

   This writes a row in `model/ids.toml`, a scenario in
   `features/suites/parsing.feature`, a failing test `parsing_cx_01` in
   `crates/conformance/tests/parsing.rs`, and the regenerated `CONFORMANCE.md`.
   Make the test assert the scenario, build the capability until it passes,
   plant the defect the test exists to catch, and run `just vv` again.

## Build from any device

`.github/workflows/build.yml` builds and verifies the app on a GitHub runner
and hands the holo back signed, so no machine of yours needs Docker, the SDK
image or a toolchain. The runner is not trusted; whoever takes the holo checks
it. Three ways in, one job:

- **From a phone or the web.** Commit an edit on github.com or GitHub Mobile.
  `pages.yml` runs the same SDK step, `prismpm verify` in the image
  `prismpm.lock` pins, signs the holo's provenance with
  `actions/attest-build-provenance`, and publishes the page, which verifies the
  holo again in the visitor's browser and links the signed provenance.
- **From a machine with Node.** `npx prism-code build --remote github` pushes
  the commit to `refs/heads/prism/build/<sha>`, waits for this workflow, and
  verifies the artifact `prism-build-<sha>` before writing anything under
  `app/.prism/build/`: the commit and repository it names, the holo's SHA-256,
  the provenance's subject and signer (a workflow of this repository through
  GitHub's OIDC issuer), the verdict, the fingerprint and every acceptance
  vector. Any of those failing is a typed refusal, not a build.
- **Run workflow**, from the Actions tab, for a branch.

`pages.yml` carries a copy of `build.yml`'s SDK and signing steps rather than
calling it: the gate pins every `uses:` to a commit and so forbids calling a
workflow by path. When one changes, copy it to the other. Pages on a private
repository needs a paid plan; the artifact and the summary need none.

## Publish the app page

`site/` is the standard Prism app page: a lean, installable PWA that loads the
holo `just app` builds, verifies it in the visitor's browser and puts the app
first. Every instance gets the same page; an app edits one file.

- **The workspace.** The page is a stage the height of the screen and never
  scrolls. A header row holds the app's name, one line under it, and View
  spec on the right. Below it, from 840 px, two panes: the app's surface on
  the left at full height, and a rail on the right with the result, the
  actions (a few of the holo's own examples, or the app's controls) and a
  history of what the visitor did, each entry one click from running again.
  An app with an input gets a display: what you type is the largest thing on
  screen, shrinking to fit as it grows, and the answer appears as you type,
  in the success colour when `app.json` calls it positive. Under 840 px the
  page is in focus mode: the surface takes the screen and one bar under it
  holds the result, then the actions, within thumb reach.
- **The spec, one click away.** View spec (or `.`, or a `#spec` link, or
  the shield's full details) opens a panel beside the window: the window
  and the bar narrow by its width (the page sets `--prism-aside` on
  `<html>`, which the frame reads) and nothing in the app moves or scales; on
  a phone the spec takes the screen. It reads in the order a newcomer asks:
  the promise and the three facts behind it (proved for every input,
  tested by the examples it carries, sealed to bytes in and bytes out), each
  theorem as it reads with its method and the rules it names (opened in
  place, read from the LexLean source under `app/src`), then the package:
  what goes in and out, every example replayed here, the fingerprint and the
  build chain. `page.mjs` renders it at build to `site/spec.html`, from
  the holo and its source; `site/spec.mjs` and `site/spec.css` load the
  first time it opens, so a visitor who only uses the app never loads them.

- **`site/app.json`** is the only file an app writes: its name, purpose and
  labels, the promise (`{ "headline", "detail" }`: one plain sentence a
  newcomer reads first, no code names, and the rule in everyday words), the
  claim, the proposition as it reads in the model, the theorems, the
  attestations, and the trusted set. Without a promise, the first plain
  sentence of the proposition stands in; `tagline` overrides the line under
  the name, which is otherwise the purpose's first sentence. `bootstrap/page.mjs` renders
  `site/index.html` and `site/manifest.webmanifest` from it; `bootstrap/icons.py`
  draws the icons (the Hologram logomark, the brand kit's 70 dots, on the warm
  ground, and `site/favicon.svg`, the mark as a vector that follows the
  browser's colour scheme, which the page carries inline as its favicon and
  its stand-in's mark, so neither costs a request), every app's default
  until it draws its own.
- **One live frame.** The frame every Prism app opens in (the top bar and
  the window the app shows through) is one web component, `<prism-frame>`, in `frame/`. On
  every push to `main`, `try-page.yml` publishes it to this repository's
  Pages site, named by its SHA-256, with a pointer:
  `https://uor-foundation.github.io/template/frame/current.json`. Every app
  page reads that pointer at run time, fetches the module it names, checks
  the bytes against the SHA-256 and only then runs it, so **a frame change
  in the template reaches every Prism app on its next load, with no app
  rebuilt.** Holo Search mounts the same element. Bytes that don't match
  the pointer never run: the page keeps its `holo://` address in the bar's
  reserved height, and the app itself still verifies and works. Offline,
  the service worker serves the last frame. `?frame=<sha256>` opens a page
  with one exact frame; `frame` in `app.json` names another frame host, for
  a test or a mirror. The frame draws in its own shadow root and brings the
  brand's tokens to a page that has none, so any host can mount it.
- **The page around it, locked.** Everything else on the page (the cards,
  renderer, loader, service worker and the page gates) is pinned by
  `frame.lock`, as `brand.lock` pins the brand: reviewed bytes that change
  only when an app chooses to. `node bootstrap/frame-sync.mjs --check` runs
  in `pages.yml` before the build, and an app takes a newer page with
  `--pin <template commit>`, which reads the template's `frame.lock` at that
  commit, fetches every file, refuses any whose bytes differ and records the
  pin. Which files a frame has is the target's to say: its `frame-sync.mjs`,
  matched to its lock, names them (inside `bootstrap/` and `site/` only), so
  a newer frame can add a file; one the target dropped is left in place and
  reported. A `frame-sync.mjs` older than this rule refuses a lock with files
  it does not know; fetch the target's script once, then pin:
  `curl -fo bootstrap/frame-sync.mjs https://raw.githubusercontent.com/UOR-Foundation/template/<commit>/bootstrap/frame-sync.mjs`.
  In the template, change these files and run `--lock`.
- **The brand is wired, not copied.** `brand.lock` pins
  [Hologram-Technologies/hologram-brand-kit](https://github.com/Hologram-Technologies/hologram-brand-kit)
  at one commit and records the SHA-256 of every file the page takes from it:
  the tokens (`site/brand/hologram-warm.css`, byte for byte) and the fonts
  (subset by `bootstrap/brand-fonts.py`, with metric-matched fallbacks).
  `node bootstrap/brand-sync.mjs --check` verifies the served files against the
  lock and runs in `pages.yml` before the build; `--pin <commit>` moves every
  app to a new kit revision. The page's own stylesheet declares no colour.
- **One frame, read like a browser.** Every app opens in the same frame: a
  46 px bar on the brand's chrome surface, and the app inside a rounded
  window inset 8 px from the screen's edges, as Lovable and Hologram OS show
  an app. The bar reads like Chrome's: home
  ([holo-search](https://uor-foundation.github.io/holo-search/)), then the
  address across the bar, the shield first, then `holo://` and the app's
  name in lower case with hyphens (`holo://luhn-check`), and the share icon
  at its right end; then GitHub (the app's repository), the theme, and full
  screen. Its icons are bare 16 px line drawings with a
  soft square tint on hover; on a touch screen each takes a 48 px tap
  beyond what it draws, so the bar is the same height everywhere. Under
  600 px GitHub steps out (the spec still links the repository); at large
  text the bar wraps and the window moves down with it. It is the live
  frame above: no app carries a copy of it.
- **Three themes: dark, immersive and light.** Plain dark, the brand's warm
  ground, is every new visitor's theme; a choice of immersive or light is
  remembered. The theme button
  shows the one in use (photo, moon or sun) and opens a panel to change it.
  Immersive is the dark ground with an Unsplash photo behind the app under
  a scrim, the rail frosted over it. The photo fills the app's window and
  stops at its edges and corners; the chrome around it never changes. A
  photo is never fetched with the page, which keeps every app inside its
  Lighthouse budget: one shown before comes from the browser's cache at
  once, and a new one arrives on the visitor's first move, its colour
  standing in until then.
  The frame draws all of it, so every Prism app and Holo Search has it with
  no rebuild. What only a visitor's move needs (every panel's styles, the
  theme panel and the photos) is a second module, `frame/panels.mjs` with
  `frame/panels.css`, published beside the frame and named by its SHA-256,
  which the frame carries: the frame fetches it after the first move,
  checks it and imports it, and a panel opened before then waits for it. Nine photos, space first, were chosen once and are published
  beside the frame (`frame/backdrops/`); the panel shows them by default, and
  the frame fetches the one in use from its own
  host, which every app page's `connect-src` already allows, and shows it
  as a `data:` image, which every `img-src` allows. No key ships, the panel
  credits each photographer, and nothing is fetched until the panel opens
  or immersive is chosen. The panel also searches Unsplash: results arrive
  as their colours, then fade in; choosing one sets it, tells Unsplash, and
  keeps it among the last three chosen. Search goes through the frame's
  worker (`frame/unsplash/`), which holds the key; the page build adds its
  origin to `connect-src`, and a page without it keeps the built-in photos.
- **The shield says why to trust the app.** As a browser's padlock does for
  a page, the shield sums what the visitor's browser found, and its panel
  shows each check: **Authentic** (every byte of the holo matches its
  fingerprint, shown with Copy), **Formally proved** (what the theorem
  guarantees, in one sentence, proved in Lean when the app was built, with
  its attestation) and **Behaves as proved** (every example the holo
  carries gives its proved answer here). Grey dots while it checks, green
  only when every check passed, red with the failing check named when one
  did not. Nothing is written by hand: `page.mjs` passes the promise's
  headline and the proof attestation from `app.json`, `app.mjs`
  passes the fingerprint check and the replay as they finish, and the
  frame draws the rest.
- **The bar holds still.** Until the frame's module arrives, the page shows
  a stand-in drawn as the bar will be: the Hologram mark and the address in
  its field, at the bar's height and in the page's theme, so the frame
  replaces it without anything moving. The stand-in is a few lines of the
  page's own CSS; writing the whole frame into every page cost about half a
  second of mobile LCP and broke the Lighthouse gate. A hop to an app the
  address bar suggested is prerendered, so it shows the full bar at once.
- **GitHub stars.** The GitHub icon in the address carries the repository's
  star count (128, 1.2k), written in at build and brought up to date from
  the Prism index on every load: no visitor's browser calls GitHub.
- **The Prism index, which every app joins by deploying.** One canonical
  kappa registry, at `registry.uor.foundation`, indexes every Prism app by
  its self-verifying address; the app's bytes stay on its own site. At the
  end of a GitHub Actions build, `page.mjs` runs `bootstrap/register.mjs`,
  which sends the registry the holo's fingerprint (its last 32 bytes) and the
  live page. The run proves its repository with the OIDC token GitHub mints
  for it, so there is no secret to hand out and a new app registers on its
  first deploy; `"index": false` in `app.json` opts out, and nothing here
  ever fails a build. The registry's indexer lists an app only when its live
  page serves a holo it registered, that holo verifies and every example
  passes; it then stores the app's address card in kappa
  (`prism/<owner>/<name>:blake3-<fingerprint>`: the fingerprint, SHA-256,
  size and where the bytes are), re-checks every app every ten minutes,
  finds new Prism apps on its own, and publishes a content-addressed
  snapshot (`/index/<sha256>.json`, named by `/index/current.json`) with
  each app's stars. Holo Search and every address bar read it downstream.
  The frame reads it at most once per page, and only when the visitor
  reaches for the bar (the GitHub pill under the pointer or in focus, or the
  address bar opened), never on load, so a page's first load keeps within
  its Lighthouse budget of two third-party requests; it checks the
  snapshot's SHA-256 before showing anything from it.
- **Hops between apps, ahead of the click.** A Prism app is named by its
  content, so a page loaded early is never stale and never another app's.
  When a visitor shows where they are going (home under the pointer, a
  suggestion chosen in the address bar) the frame marks that page with a
  `data-prism-ahead` link, and the page's one speculation rule (fixed, so
  `page.mjs` hashes it into the Content-Security-Policy) has the browser
  prerender it: the next app loads, verifies its bytes and replays its
  examples before the click, so opening it shows a page already checked.
  Another origin is prefetched; a browser without speculation rules gets a
  prefetch. Each page also opens the frame host's connection with its own,
  and holds the bar in place across the navigation with a cross-document
  view transition.
- **An address bar for Prism apps.** The holo:// pill is also an omnibox,
  like Chrome's. Focus it and it selects the address, a hairline in the UOR
  Foundation's colour spectrum runs round it, and it lists this app, every
  app in the Prism index (most stars first, each opening its own live page)
  and every entry in [Holo Search](https://uor-foundation.github.io/holo-search/)'s
  registry, one row each: the app's icon (its live page's, else its initial
  on a hue taken from its fingerprint, as a browser shows a site with no
  icon), its name, its address or short hash, and on the right its GitHub
  owner and stars. Type a name or a hash prefix to
  filter; paste a full address (a sha256 or blake3 digest, an IPFS CID, a
  Holo Search link) to open it. Enter hands it to Holo Search as `?r=`,
  which fetches the app, checks the bytes against the address and replays
  its examples before it opens: this page only suggests, Holo Search
  verifies. Arrows move, Escape backs out, and on a phone the bar takes the
  whole width while you type. The registry is fetched the first time the
  bar is focused, and the index with the page; the Content-Security-Policy admits
  Holo Search's origin for that request and the search form. Without a
  script, Enter still submits the form to Holo Search.
- **One Prism account, no password.** The person icon after full screen
  signs the visitor in with the device's own passkey (Face ID, Touch ID,
  Windows Hello, a phone), whose key never leaves its secure hardware. The
  account is named by its key's hash and the frame checks every signature
  in the browser, so no server is trusted to say who is signed in. See
  [identity/README.md](identity/README.md).
- **Made to be shared.** `bootstrap/og.py` draws `site/og.png`, the 1200 x
  630 card every platform shows for the link (the brand's dark ground, the
  mark, the app's name and purpose, "Proved in Lean. Verified in your
  browser."), from `app.json` and the page's own fonts. Run it whenever the
  name, purpose or live URL changes and commit the image; `page.mjs` refuses
  to render without it and writes the Open Graph and Twitter Card tags, all
  absolute on the live URL. On a phone the share button opens the system
  share sheet. Elsewhere it opens a panel with the card as the platforms
  will show it, the link to copy, and X, LinkedIn, Facebook and email (and
  the system sheet, where the browser has one). The card is fetched only
  when the panel first opens, never with the page.
- **The page is this app's, not the template's.** A repository created
  from the template starts with the template's `app.json`, social card and
  icons, and `bootstrap/page.mjs` refuses each until it describes this app.
  In CI, `app.json`'s `repository` must be the repository being built.
  `og.py` and `icons.py` stamp every PNG with a SHA-256 of what it was drawn
  from (the name, purpose and live URL, and the script's own bytes); the
  renderer recomputes the stamp from `app.json`, so a card or icon drawn for
  another app, left stale by an edit, or drawn by an older script never
  ships: run `python -I bootstrap/og.py` and `python -I bootstrap/icons.py`
  (after `node bootstrap/brand-sync.mjs --sync`, for the icons' font).
  `pages.yml` draws both before it renders, with Pillow pinned by hash in
  `bootstrap/draw-requirements.txt`, so publishing needs neither Python nor
  Pillow on the author's machine; drawing locally only refreshes the
  preview. An app pinning this page for the first time redraws both once. And
  `frame-sync.mjs --lock` runs only in this repository, so no app can bless
  its own copy of the page.
- **Any screen.** Material 3 window size classes: focus mode under 840 px,
  the workspace's two panes from 840; 16 px margins under 600 px and 24 px
  from it; 48 px touch targets on coarse pointers; safe areas; forced colours
  and reduced motion respected. `bootstrap/screens.mjs` holds every class
  in every theme to it, with the spec open and closed, and fails a page that
  scrolls.
- **An app's own surface.** An app that needs more than an input (a chess
  board) adds `site/card.html`, `site/card.css` and `site/card.mjs`. Each part
  of `card.html` names the workspace slot it fills with `data-slot`:
  `surface` (the stage, as large a square as fits), `result`, `actions` and
  `history` (the rail, `data-label` naming the last two), and `evidence`
  (the spec). A small script `page.mjs` hashes into the page moves each
  part into place before first paint, so nothing shifts; `card.mjs` is
  started with the verified app and finds its parts by id, as before.
- **Installable and offline.** A manifest with maskable icons and a service
  worker that caches every response as it passes, so the app loads, verifies
  the holo and answers requests with the network off after one visit. A new
  deploy shows one "Update available" chip and reloads only when asked.
- **The gate.** `lighthouserc.json` asserts 100 in performance, accessibility,
  best practices and SEO on the mobile profile, LCP under 1.5 s, TBT under
  100 ms, CLS 0, under 120 KiB and at most two third-party requests (the
  frame's pointer and module); `pages.yml` runs
  Lighthouse CI on the assembled site before anything is deployed.

`.github/workflows/pages.yml` checks the brand wiring on every push to
`main`, builds and verifies the holo through the locked SDK, signs its
provenance, renders the page with that holo and the provenance link, writes
the precache list, runs Lighthouse, and publishes to GitHub Pages. Turn Pages on
once, with the workflow as its source:

```sh
gh api -X POST repos/OWNER/NAME/pages -f build_type=workflow
```

The page is then at `https://OWNER.github.io/NAME/`. The workflow runs beside
`bootstrap`, not after it: `just app` is the proof-bearing build, so the page
goes live as soon as the Lean kernel has accepted the model.

## Everyday commands

| Command | What it does |
| --- | --- |
| `just vv` | The whole gate: format, model and audits, the SDK's template and lock checks, Clippy over every feature, the tests, `cargo deny`, and the Prism app's verified build. |
| `just app` | Checks the Prism application's model is canonical and locked, then builds and verifies its holo. |
| `just new-capability <ID> <level> <suite> "<statement>"` | Registers a capability with its scenario and failing test (R3). `level` is `build`, `open` or `some-true`. |
| `just model-write` | Regenerates `CONFORMANCE.md` from `model/`. |
| `just fmt` | Formats the workspace. |
| `just bdd` | Runs only the conformance meta-gate while you write scenarios. |
